# 小游戏接近完工时的质量审计

## 何时启动

用户要求：每款小游戏接近完工时，创建多个子 agent 审计 UI 和其他方面；保证质量，同时避免过度严格、不停重试浪费 token 与时间。

当主要玩法与配置已接好、能构建、基本进入与退出流程可以检查时，主 agent 启动一次集中审计。先给出游戏范围、变更文件、构建版本、验证入口、已知限制；不要给每个子 agent 复制全部项目历史。大型功能重制适用同一规则，文档小改、目录整理或普通小修不自动触发全组。

## 三个并行子任务

| 子 agent | 重点 | 输入与产出 |
| --- | --- | --- |
| UI 与操作 | 文字可读性、遮挡/溢出、牌面与角色布局、点击与拖动、暂停与返回、动画状态、目标分辨率/缩放 | 优先检查实际截图或可运行界面；源码推断必须标注。报告影响玩家操作的问题，纯审美建议另列 |
| 玩法与配置 | 规则胜负、关卡、CFG 默认值及作者覆盖、UP 社交和剧情绑定、费用/奖励恰好结算一次 | 定向规则测试和实际配置路径；核查失败、认输、重开、重复进入、读档失效 |
| 稳定性与交付 | 对象/协程/音频/事件释放，存档隔离，资源遗漏，单 DLL 和 Steam 布局，前置兼容 | 受影响的构建、打包或运行证据；区分持续增长的泄漏与合理缓存，不凭一次内存峰值断言泄漏 |

主 agent 负责并行运行必要回归、合并重复发现和实施修复。子 agent 默认只读；若明确分配修复，只修改自己的文件范围。子 agent 不再派生审计 agent。

## 发现问题的要求

每名子 agent 通常只返回最重要的 5 个可操作问题，同源问题合并；明确且独立的阻断项不得因数量上限被隐藏。每项包括：严重程度、复现条件或具体证据、文件/界面位置、影响、建议的最小修复。没有发现阻断项就明确写出，并说明已检查和未检查内容。没有证据的可能性放入待验证项，不能写成已确认缺陷。

- **阻断**：可复现的崩溃、丢档、污染其他 Mod/存档、奖励或费用重复、错误胜负、主流程不能完成、配置/关卡绑定不生效、包无法加载。
- **本轮应修**：影响主要操作的遮挡、不可读文字、错位点击区域、卡住的动画/输入等明确 UI 问题。修复范围应与证据一致。
- **不阻断**：轻微美观偏好、可用但不够精致的动画、范围外重构、未证实的极端情况。记入后续工作，不借此扩大任务。

不设置任意“必须 95 分”等门槛，也不要求所有建议清零。真实严重问题不能为赶进度降级；主观偏好不能升级成阻断。

## 复核与停止

默认 **1 轮集中审计 + 最多 1 轮针对修复的复核**。复核沿用原 agent，只给差异和必要上下文；只运行受影响测试，不把其他已通过模块再审一遍。无新改动、失败或明确新风险时停止扩大检查。

若复核仍有阻断项，主 agent 报告具体残留问题并继续定向修复，保留问题追踪；不得把“再叫一整组 agent 审一遍”当作解决办法。新增独立功能或大范围改动才启动相应新审计，并说明范围变化。

交付条件：阻断项已解决、受影响的必要回归通过、当前构建与配置对应、明显操作问题已处理，并准确列出未验证环境。若缺少真实 UI/原生运行条件，记录为未验证；可以按用户授权交付测试版，但不能声称完成正式实机验收。

## 精简记录

在具体任务的 QA 目录保留版本/提交、三个审计范围、发现与处理、测试结果、未验证项即可，不上传长对话。现行知识仅写长期适用结论；公开报告不得包含玩家存档、私人路径、账号和日志敏感内容。
